형식: **제약 → 문제 → 실험/측정 → 결과 → 바꾼 것**. 수치는 실제로 잰 값만 적는다. 아직 하지 않은 평가는 맨 아래 "계획"에 둔다.

데이터: 본인 카드 내역 446건(2026-05-01 ~ 10-13, 카드 4장: 현대·롯데·신한·토스뱅크). 원본은 저장소에 없다.

## E1. 카드사 파일 가져오기 검증 (10/13)

- **제약**: 개인은 마이데이터·카드사 API를 쓸 수 없다. 카드사마다 내보내기 형식이 다르다(롯데 이용내역 .xls, 현대·신한 명세서 .xls — 실제로는 HTML, 토스 후불교통 PDF).
- **문제**: 형식이 제각각이고 현대 명세서는 할부가 회차마다 여러 파일에 반복된다. 잘못 합치면 월 합계가 틀린다.
- **측정**
  - 롯데 파일 5개: 파일 머리글의 건수·금액합계와 파싱 결과 비교 → **5/5 일치**(취소 2건 제외 규칙 확인)
  - 토스 PDF: 61건, 49,600원 → 내역서 합계와 **일치**
  - 현대 할부: (이용일, 가맹점, 총액)으로 하나만 남김
  - 앱 계산 엔진(Dart)으로 다시 계산한 5~10월 월 합계가 Python 분석과 **원 단위까지 일치**(테스트로 고정)
- **발견**: 롯데 해외 결제에 "통화 없음 + 매입 N" 소액 행(가승인)이 있고 파일 합계에서 빠진다 → 저장하지 않도록 규칙 추가

## E3. 문제 정의 수정: "월말 과소비"는 사실이 아니었다 (10/13)

- **가설(PRD 초안)**: 월말에 공과금·통신비가 나가면서 많이 쓴다.
- **측정**: 5~9월 지출을 1~10일 / 11~20일 / 21일~말일로 나눔 → 월말 구간이 가장 큰 달은 **5개월 중 0개월**(월초가 가장 큰 달 2개, 중순 3개). 통신비는 월말이 아니라 11~13일에 나간다.
- **바꾼 것**: 핵심 화면을 "월말 경고"가 아니라 **매일 보는 "오늘 쓸 수 있는 금액"**으로 확정. 정기 지출은 월초에 미리 빼서 결제일에 하루 금액이 흔들리지 않게 설계

## E4. 카테고리 추천: 규칙 → 라벨 정리 → 애매한 가맹점 분리 (10/13)

- **제약**: LLM 호출은 비용·지연이 있으므로 흔한 가맹점은 규칙으로 처리(PRD: LLM 호출 30% 이하 목표).
- **측정**: 사용자가 446건에 정답 라벨을 붙인 뒤 규칙 추천과 비교

  | 단계 | 일치 | 규칙이 못 정함 |
  |---|---|---|
  | 규칙 v1 | 421/445 (94.6%) | 16건 |
  | 라벨 기준 정리 + 금액·반복 규칙 추가 | 432/446 (**96.9%**) | 12건 |

- **오류 분석**: 틀린 것 대부분이 **같은 가맹점에 정답이 둘 이상**인 경우였다(구글플레이 = 구독 + 게임 추가 결제, 구글클라우드 = API 사용료 + 가끔 다른 결제, 네이버페이 = 여러 쇼핑몰).
- **바꾼 것**
  - 구글플레이: 같은 금액이 3개월 이상 반복되면 구독, 아니면 게임
  - 구글클라우드: 1만 원 이상이면 기타, 미만이면 API
  - 네이버페이처럼 규칙으로 못 푸는 결제대행형 가맹점은 **"애매함" 목록**으로 분리 → 확인 화면에서 사용자에게 먼저 묻고, 한 번 고른 값을 다음 결제에 학습하지 않음
  - 분류 모델(jev)의 확신도가 기준(처음 0.8, E10 이후 0.95) 미만이면 같은 "애매함" 경로로 보냄
- **한계**: 규칙을 같은 데이터를 보며 만들었으므로 96.9%는 낙관적인 값이다. 실사용(새 결제)의 추천 수락률로 다시 잰다(앱 "사용 기록"에 기록 중).

## E5. 정기 지출 자동 탐지: 오탐 줄이기 (10/13)

- **규칙 v1**: 같은 가맹점이 연속 2개월, 결제일 ±3일, 금액 차이 ≤10%면 고정, 넘으면 추정(공과금형)
- **측정(실데이터)**: 16개 제안. 이 중 **이마트24, 티머니 고속버스는 우연히 2개월 겹친 오탐**
- **바꾼 것(v2)**: 금액이 바뀌는 추정형은 **연속 3개월 이상**만 제안
- **결과**: 13개 제안. Spec에 적어 둔 필수 항목 9개(통신·인터넷·전기·가스·Cursor 등) **모두 포함**, 알려진 오탐 0개. 대신 2개월뿐인 야쿠르트(금액 변동)는 놓친다 → 정밀도를 택하고, 놓친 항목은 직접 추가로 보완
- **추가 결정**: 매칭에서 **카드 조건을 뺐다**. 실데이터에서 8월에 구독 3개가 현대 → 롯데로 옮겨 갔는데 카드를 조건에 넣으면 매칭이 끊긴다.

## E6. 알림이 없는 지출: 교통비 월 예약형 (10/14)

- **제약**: 토스 후불교통은 탈 때마다 알림이 오지 않는다 → 알림 기반 기록이 불가능
- **측정**: 출근일 하루 교통비가 거의 일정(3,100원 = 버스 1,500 + 지하철 50 + 1,550. 탄 17일 중 15일이 정확히 3,100원)
- **설계**: 정기 지출에 "월 예약형"을 추가. 예상액(탄 날 하루 합계 중앙값 × 이번 달 평일 수 = 3,100 × 22 → 69,000원)을 월초에 미리 떼고, 실제 결제가 들어오면 그만큼 줄인다. 오늘 탄 교통비는 예약분 안에서는 "오늘 쓸 수 있는 금액"을 줄이지 않는다.
- **결과(10/13 기준)**: 10월 교통비 18,600원 사용 → 남은 예약 50,400원이 예정 지출에 들어가고, 평소 소비 예측(P)에서 교통비가 빠져 이중 계산이 사라짐

## E7. 구매 상담 에이전트: 숫자 환각 막기 (10/14)

- **제약**: 돈 이야기에서 틀린 숫자는 치명적이다. LLM이 계산하게 두면 안 된다.
- **설계**
  - 모든 계산은 앱 코드(툴)가 하고, LLM은 툴 결과의 `*_text` 값만 인용
  - "살지 말지" 판단도 코드가 내린다(예상 월말 지출 vs 예산, 10% 경계). LLM은 그 판단을 설명만 한다
  - 서버가 최종 답의 **금액**을 툴 결과·사용자 입력과 대조하고, 판단 문구가 코드 판단과 같은지 확인 → 실패하면 1회 재생성 → 또 실패하면 숫자 없는 대체 문구
  - 횟수·날짜("2번", "12일")는 대안 제시에 자연스럽게 나와서 검증 대상에서 뺐다(넣으면 정상 답도 막힘)
- **측정(실제 gpt-6.1-sol, 가짜 숫자 시나리오 4개)**: 검증 통과 4/4, 판단 일치 2/2(구매 질문), 투자 질문은 LLM 호출 없이 거절, 금액 없는 질문은 금액을 되물음. 1회 2~3 라운드, **4~11원**
- **발견 → 수정**: "남은 예산은 -3,500원"처럼 음수를 그대로 말함 → 지시문에 "음수는 'N원 넘어요'로" 추가 → 재실행에서 해결

## E10. 카테고리 분류 모델 비교와 jev 확신도 보정 (10/15)

- **질문**: 처음 보는 가맹점은 jev(빠르고 싸고 확신도를 줌)와 gpt-6-luna 중 무엇을 쓸까? 확신도 기준 0.8은 맞나?
- **방법**: 사용자 라벨 446건(가맹점 109개, 카테고리 15개)을 jev·luna·내장 규칙으로 각각 분류해 거래 단위로 비교(`server/eval/run_category.py`). 가맹점 이름만 보는 분류의 상한은 98.4%(같은 가맹점에 정답이 둘 이상인 경우 때문)
- **결과**

  | 방법 | 정확도 | 지연 p50 | 비용(109회) |
  |---|---|---|---|
  | 내장 규칙(같은 데이터로 만든 낙관값) | 96.9% (적용률 97.3%) | 즉시 | 0원 |
  | jev 단독 | 76.7% | 0.62초 | 3.6원 |
  | gpt-6-luna 단독 | 83.0% | 1.23초 | 4.4원 |
  | 규칙 → jev | 97.3% | | |
  | 규칙 → luna | 98.2% | | |

  jev 확신도 구간별 정답률:

  | 확신도 | 거래 비율 | 정답률 |
  |---|---|---|
  | 0.95 이상 | 65.0% | **99.7%** |
  | 0.90~0.95 | 1.8% | 25.0% |
  | 0.80~0.90 | 3.6% | 37.5% |
  | 0.60~0.80 | 9.9% | 31.8% |
  | 0.60 미만 | 19.7% | 35.2% |

- **해석**
  - jev는 **확신할 때는 거의 틀리지 않지만**(0.95 이상 99.7%), 그 아래로는 구간과 상관없이 30% 안팎으로 떨어진다. 확신도가 "맞을 확률"이라기보다 "아는 가맹점인지"를 가르는 신호로 동작한다
  - 지금 기준 0.8은 정답률 30%대 구간(0.8~0.95, 거래의 5.4%)을 그대로 통과시킨다
  - 규칙이 못 정한 거래(개인 가게 등 12건)만 보면 jev 16.7%, luna 50% — 표본이 작지만 "처음 보는 가맹점"에서는 luna가 낫다
- **바꾼 것(10/15 적용)**: 확신도 기준 0.8 → **0.95**. 그 아래는 "애매함"으로 표시해 확인 알림에서 [수정]을 먼저 보여준다(서버 `JEV_MIN_CONFIDENCE`, Cloud Run 반영). 실사용 추천 수락률로 다시 확인

- **해석**
  - 이 평가셋에서는 **luna/low가 sol과 같은 점수를 1/19 비용, 더 짧은 지연으로** 냈다. 판단을 코드가 내리고 숫자를 서버가 검증하는 구조라 LLM에 남은 일(금액·날짜 읽기, 설명)이 작은 모델로도 충분했던 것으로 본다
  - 추론 none은 지연이 오히려 길고(p90 14초) 툴 오사용이 남음 → "추론 없음"이 늘 빠른 것은 아니다(라운드 수·재시도 영향)
  - 개선 폭은 모델 교체보다 **컨텍스트(오늘 날짜) 한 줄**이 컸다
- **한계**: 가짜 숫자의 단일 턴 질문이라 쉬운 편이고 이미 100%에 닿았다(포화). 답의 말투·대안의 질은 재지 않았다
- **다음**: (1) 상담 기본 모델을 luna/low로 바꾸고 숫자 검증 실패 시에만 sol로 재생성하는 단계 구조 검토 (2) 더 어려운 평가셋 v2: 여러 턴 대화, "그럼 반값이면?" 같은 후속 질문, 모순된 요구, 여러 물건 합산 (3) 말투·대안 품질 채점(jev score 루브릭 등)
