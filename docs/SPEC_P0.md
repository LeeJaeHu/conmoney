# Spec — 월 예산 에이전트 P0

- 작성: 2026-10-13 · 상태: 초안 v0.1 · 근거 문서: [PRD_budget_agent.md](PRD_budget_agent.md) v0.2
- 범위: PRD의 P0 기능(F1–F8)을 구현하는 데 필요한 동작, 데이터, 계산, 인터페이스, 수락 테스트
- 표기: `[가정]` = PRD에 없어 이 Spec에서 정한 값(바꿔도 됨) · `[확인 필요]` = 실제 데이터로 검증해야 함 · `[PRD 수정 제안]` = PRD와 충돌하거나 PRD에 보완이 필요한 부분

## 0. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 금액 | 원 단위 **정수(int)**. 소수 없음. 지출은 양수, 취소·환불은 음수 |
| 시간대 | 모든 날짜 계산은 `Asia/Seoul` 기준. DB에는 UTC epoch ms와 함께 로컬 날짜(`yyyy-MM-dd`)를 저장 |

| ID | 로컬 DB는 정수 auto-increment. 서버로 보내는 데이터에는 ID 대신 집계값만 포함 |

### 2.2 가맹점 정규화 `merchant_norm`
1. 앞뒤 공백 제거, 연속 공백 1개로
2. 전각 → 반각, 영문 대문자화
3. 괄호 안 지점명 제거 안 함(지점 단위 학습을 막지 않기 위해) `[가정]`
4. 끝에 붙는 `(주)`, `주식회사`, `㈜` 제거
5. 결제대행 접두어는 **제거한다**(실데이터 확인). 현대카드는 `{PG} - {가맹점}` 형식: `KCP`, `나이스`, `(주)이니시스`, `토스페이먼츠`, `한국정보통신`, `카카오`, `씨제이시스템즈(주)`, `신한은행`. 롯데카드는 `{가맹점}_{법인명}` 형식(예: `우아한형제들_주식회사우`)
6. 같은 가맹점이 카드사마다 다르게 찍힌다. 현대는 해외 가맹점명을 20자에서 자르고(`CURSOR, AI POWERED I`), 롯데는 법인명을 덧붙인다(`네이버플러스 멤버십_네이버` vs `네이버플러스멤버십`). 그래서 **별칭 테이블**(`merchant_aliases`: 패턴 → 대표 이름)을 두고, 초기값은 `tools/import_statements.py`의 `norm_merchant` 규칙을 옮긴다
7. 현대카드 해외 결제는 가맹점명 끝에 `,USD:6.60` 형식으로 원통화가 붙는다 → 떼어서 `original_amount`로

## 3. 계산 명세 (BudgetEngine)

PRD 7장을 코드로 옮길 수 있게 정의한다. 모든 함수는 **기준 시각 `now`를 입력으로 받는 순수 함수**로 만든다(테스트 가능, 0시 작업 누락에도 결과 동일).

### 3.1 기호
- `m` = now가 속한 월, `D` = m의 일수, `d` = 오늘 날짜(일), `today` = now의 local_date
- `N` = 오늘 포함 남은 일수 = `D − d + 1`

### 3.2 거래의 월 기여액 `contrib(tx, m)`
| 경우 | 기여액 |
|---|---|
| kind=APPROVAL, status=CANCELLED | 0 |
| APPROVAL, 일시불, local_date ∈ m | amount |
| APPROVAL, 할부 | m 월의 installment_schedules(voided=false) 금액 합 |
| CANCEL / MANUAL | local_date ∈ m 이면 amount(음수 가능) |

### 3.3 확정 지출 S
`S(m) = Σ contrib(tx, m)` (모든 거래, 특이 지출 포함, 미확인 포함)

`S_before_today = S(m)` 중 **오늘 승인·취소된 거래의 기여분을 뺀 값**.
- 이전 달에 산 할부의 이번 달 회차는 "오늘 거래"가 아니므로 항상 S_before_today에 들어간다. 즉 할부 이월분은 **매월 1일 0시에 확정 지출로 잡힌다.**

### 3.4 예정 지출 F
`F(m, at) = Σ 활성 정기 지출 중, 시각 at 기준으로 m 월에 PAID/SKIPPED 기록이 없는 항목의 amount`
- due_day가 D보다 크면 말일로 본다.
- 예정일이 지났는데 결제가 안 들어온 항목도 **월말까지 F에 남긴다**(늦게 빠져나가는 경우 대비). 예정일 + 3일이 지나면 정기 지출 화면에 "아직 결제 안 됨"으로 표시하고, 사용자가 [이번 달 없음]을 누르면 SKIPPED로 바꾼다.
- `[PRD 수정 제안]` PRD 7장의 "이번 달 청구 예정인 할부금 중 S에 없는 것"은 3.3절 규칙(이월 회차는 1일에 S로 확정)에 따라 **항상 0**이다. PRD에서 이 항을 삭제하거나 "이월 할부 회차는 매월 1일에 S로 확정"으로 바꾸는 것을 제안한다.

### 3.5 남은 예산
`R = B − S(m) − F(m, now)`

### 3.6 오늘 쓸 수 있는 금액
```
R0        = B − S_before_today − F(m, 오늘 0시)       // 오늘 0시 기준 남은 예산
base      = floor(R0 / N)                              // 하루 기준액 (음수 가능)
spent_today = Σ 오늘 거래의 기여분
              − Σ 오늘 정기 지출에 매칭된 거래의 예정액   // 이미 F로 빼둔 만큼은 이중 차감하지 않음
available = base − spent_today
```
- 표시: `available ≥ 0` → `available`, `available < 0` → **0원** + "오늘 {−available}원 초과" 보조 문구
- `R0 < 0`이면 base도 음수 → 0원 + "이번 달 예산을 {−R0}원 넘었어요" 문구(비난 없는 말투, 8장)
- **base 재계산 시점**: 0시 작업, 또는 사용자가 **예산 금액·정기 지출을 바꿨을 때**(그날 기준액 다시 계산). 결제가 들어와도 base는 바뀌지 않는다.
- `F(m, 오늘 0시)`를 다시 구하려면 "오늘 생긴 PAID/SKIPPED 기록"을 무시하고 계산하면 된다. 그래서 0시 작업이 빠져도 앱을 열 때 같은 값을 만들 수 있다. `daily_bases`는 캐시일 뿐이다.

**계산 예** (10월, D=31, 오늘 13일 → N=19)
- B = 1,000,000 / S_before_today = 600,000 / F = 115,000(통신 65,000 + 가스 50,000)
- R0 = 285,000 → base = 15,000
- 오늘 스타벅스 6,500원 → available = 8,500원
- 오늘 통신비가 실제 66,000원 결제됨 → spent_today 증가분 = 66,000 − 65,000 = 1,000 → available = 7,500원

### 3.7 평소 패턴 P
"남은 기간에 평소 얼마나 쓰는지"를 추정한다. 예상 월말 지출 `E = S + F + P`에서 F와 겹치지 않도록 **정기 지출에 매칭된 거래와 할부 이월 회차는 제외**한다.

```
var_spend(month, from_day, to_day) =
   Σ 해당 월 from_day..to_day 거래의 기여액
   (is_unusual=false, recurring_item_id=null, 이전 달 할부의 이월 회차 제외)

P(now) = median over k ∈ {최근 완료된 월 최대 3개, 데이터가 있는 월만}:
           var_spend(m−k, min(d, D_k), D_k)
```
- 비교 월이 더 짧으면 날짜를 말일로 맞춘다(예: 31일 기준 → 2월은 28일).
- 첫 기록일 이후 **전체 기간 데이터가 있는 월**만 쓴다(설치 도중의 달은 제외).
- **데이터 부족 대체값**: 쓸 수 있는 달이 0개면 `P = floor(var_spend(m, 1, d−1) / (d−1) × N)` (이번 달 일평균 × 남은 일수). d=1이면 P=0. 이때 결과에 `pattern_source = "THIS_MONTH_PACE"` 또는 `"NONE"`을 붙여 에이전트가 "아직 기록이 적어요"라고 말할 수 있게 한다.
- `[PRD 수정 제안]` P0에는 과거 기록 가져오기(F10)가 없어서, 설치 후 최소 1~2개월은 P와 정기 지출 자동 탐지가 대체값으로만 동작한다. 그래서 **개발자용 CSV 가져오기(설정 > 개발자 메뉴, UI 최소화)** 를 P0에 넣는다.
  - 카드사 파일 → CSV 변환은 PC에서 `tools/import_statements.py`로 한다(롯데·현대·신한 .xls, 토스 후불교통 PDF 지원). 앱은 CSV만 읽는다.
  - CSV 열: `date,time,card,merchant,merchant_raw,amount,installment_months,is_foreign,currency,original_amount,cancelled,category,category_guess,is_unusual,source`
  - 현재 `data/transactions_v3.csv`에 2026-05~10-13 446건. **5~9월 5개월을 P 계산에 쓴다**(10/13 결정: 5월 롯데 사용은 거의 없었으므로 5월도 전체 데이터로 봄).
  - `is_unusual`은 `UNUSUAL_RULES`(현재 `닌텐도`)로 채운다. 10/13 결정: 닌텐도 결제는 특이 지출.
  - **검수 라벨**: `data/transactions_checked.csv`(사용자 검수본, 10/13)가 있으면 스크립트가 같은 거래(날짜·카드·원문 가맹점·금액·같은 키 안에서의 순서)를 찾아 `category`(정답), `is_foreign`, `cancelled`를 가져온다. `category_guess`는 항상 규칙 추정값이라 둘을 비교하면 규칙 정확도가 나온다
  - `is_foreign`: 해외 가맹점이어도 **원화로 결제하면 해외 결제가 아니다**(검수 결과, 예: Cursor `KRW:30106`)

### 3.8 구매 판단
```
E_after = S + F + P + contrib_this_month(구매)   // 할부 구매면 첫 회차만
over    = E_after − B
verdict = over ≤ 0            → OK         ("괜찮아요")
          over ≤ floor(B×0.1) → CONDITIONAL ("조건부")
          그 외               → POSTPONE    ("미루는 걸 추천")
```
- 판단은 **코드가 내린다.** LLM은 `verdict`를 바꾸지 않고 설명만 한다.
- **다음 달 이후 구매**(10/15 변경, 이전에는 NEXT_MONTH로 판단 보류): 그 달 M 기준으로 같은 규칙을 쓴다.
  ```
  E_M = known_M(이미 정해진 할부 회차) + fixed_M(활성 정기 지출 전체 + M의 예정 지출) + usual_M + 1회차
  usual_M = 최근 완료된 달(최대 3개) 전체 기간 varSpend의 중앙값 (없으면 이번 달 일평균 × M의 일수)
  B_M = M의 예산. 없으면 직전 달 예산을 이어 쓴다(budgetFor)
  ```
- **할부 대안**: 일시불 판단이 OK가 아니면 2·3개월 할부안을 같이 계산한다. 회차마다 그 달(구매 달은 위 이번 달 식, 이후는 E_M 식)에 회차 금액을 더해 판단하고, 가장 나쁜 판단을 그 안의 판단으로 본다. 무이자 여부는 앱이 알 수 없으므로 카드사 확인을 안내한다. [판단] 줄은 일시불 판단 그대로.
- **금액 범위 질문**("10만 원대"): 되묻지 않고 범위를 판단별 구간으로 나눈다. `ok_up_to = −over(0원)`, `conditional_up_to = floor(B×0.1) − over(0원)`, 둘 다 1,000원 단위 내림(보수적). 일시불 기준.
- **예정 지출**(축의금 등 한 번 나갈 돈): 낼 날짜가 속한 달의 F에 더한다. [냈어요]를 누르면 같은 금액의 MANUAL 거래(특이 지출, 이름에 축의·선물 등이 있으면 경조사·선물)가 생기고 F에서 빠진다. 오늘 낸 것은 0시 기준 F에 남겨 오늘 금액이 이중으로 줄지 않게 한다(정기 지출 매칭과 같은 방식). 상담에서 제안하면 화면의 [등록]을 눌러야 저장된다.
- 테스트: C19(다음 달 판단·예산 이어 쓰기), C20(할부안), C21(예정 지출 F), C22(범위 경계)

### 3.9 F7 페이스 판단
"남은 예산이 예정보다 빠르게 줄어듦" = `E(now) > B` 이고 **어제 0시 기준 E는 B 이하였음**(새로 넘어선 날만 1번) `[가정]`.

**처리 순서**
1. 리스너가 알림 수신 → F1 필터 통과 시 `raw_notifications`에 저장
2. 같은 `notif_key` + 같은 본문 해시가 이미 있으면 무시(알림 갱신·재게시 대비)
3. 출처별 파서 실행 → `ParsedPayment` 또는 `ParseFailure`
4. 취소면 4.4절, 승인이면 중복 검사(4.3절) 후 저장
5. 할부면 할부 일정 생성(4.5절), 정기 지출 매칭(F5), 카테고리 추천(F3) → 확인 알림

**파서 인터페이스**
```dart
abstract class PaymentParser {
  String get sourceKey;                      // HYUNDAI_APP 등
  bool isPaymentLike(String title, String text); // 결제 관련 알림인지 (광고·공지 제외)
  ParseResult parse(String title, String text, DateTime postedAt);
}

class ParsedPayment {
  final String? last4;
  final int amount;            // 원화. 해외 원통화만 있으면 0 + foreignAmount
  final String? foreignAmount; // "USD 12.99"
  final String merchant;
  final DateTime approvedAt;   // 본문 시각 우선, 없으면 postedAt
  final bool isCancel;
  final int installmentMonths; // 일시불 1
  final bool isForeign;
}
```
- 규칙은 출처별 정규식 목록으로 두고, **실제 알림 샘플을 모은 뒤 작성한다**(열린 질문 4). 샘플 → 정규식 → 평가셋 회귀 테스트 순서.
- **구현 (10/17)**: 롯데카드 알림톡만 샘플이 있어 파서를 만들었다(`app/lib/core/payment_parser.dart`). 형식은 `가맹점 / N원 승인 / 이름 카드명(번호) / 일시불, MM/dd HH:mm / 누적금액`. 10/18 현대카드 앱 추가: `이름 님, 현대 ZERO 승인 N원 일시불, MM/dd H:mm / 가맹점 / 누적N원`(가맹점은 big_text에만 있음). 원문은 네이티브 `raw_notifications.db`에 두고, 처리 결과(`SAVED/DUP/CANCEL/IGNORED/PARSE_FAIL/UNSUPPORTED`)는 앱 DB `notification_results`(v6)에 남긴다. 파서가 없는 출처는 `UNSUPPORTED`로 두었다가 동기화 때마다 다시 본다. 동기화 시점은 홈을 열 때·앱으로 돌아올 때·당겨서 새로고침 `[가정]`(앱이 꺼져 있는 동안은 반영 안 됨)
- 공통 키워드 `[확인 필요]`: 승인/취소(`승인`, `취소`, `승인취소`), 할부(`(\d+)개월`, `일시불`), 해외(`해외`, 통화 코드 `USD|EUR|JPY|...`), 금액(`([\d,]+)원`)
- `isPaymentLike = false`(광고, 명세서 안내 등)는 `IGNORED`로 원문만 남긴다.
- `isPaymentLike = true`인데 parse 실패 → `PARSE_FAIL`로 needs_review 거래 생성(amount=0, 원문 보존). **조용히 버리지 않는다.**
- 본문에 연도가 없으면 postedAt의 연도를 쓰되, 1월에 12월 날짜가 오면 전년으로 본다.
- 해외 결제에 원화 금액이 없으면 `FOREIGN_AMOUNT` needs_review: 확인 시트에서 원화 금액을 입력받는다. 입력 전에는 기여액 0 `[가정]`.

**4.3 중복 처리**
- 저장 전, 같은 `dedupe_key`이거나 **같은 금액 + 승인 시각 ±3분 + 다른 출처**인 거래가 있으면 새 거래를 만들지 않고 `raw_notifications.result = DUP`로 연결만 한다.
- 가맹점명이 달라 확신할 수 없는 경우(금액·시각만 일치)는 둘 다 저장하고 나중 것에 `DUP_SUSPECT` needs_review → 사용자가 [같은 결제] / [다른 결제] 선택.
- 토스 교통 후불은 다른 카드로 청구되지 않으므로(F1) 위 일반 규칙만 적용한다. 환승 0원·50원 승차도 건별로 들어오므로 **0원 거래는 저장하되 확인 알림을 보내지 않는다** `[가정]`.
- **가져온 기록과 알림 거래의 중복**: 현대카드 명세서에는 시각이 없다(가져온 기록의 약 51%가 시각 없음). 시각이 없는 쪽이 있으면 `같은 카드 + 같은 날짜 + 같은 금액 + merchant_norm 일치`로 비교한다.

**4.4 취소 처리**
1. 원거래 후보 = 같은 카드, kind=APPROVAL, status=ACTIVE, 같은 금액, 최근 90일, merchant_norm 일치(또는 앞 6자 일치) → 가장 최근 1건
2. **찾음 + 같은 달**: 원거래 status=CANCELLED, CANCEL 행(amount=−금액, cancel_of_id 연결)은 합계 계산에서 제외. 할부면 모든 회차 voided
3. **찾음 + 이전 달**: 원거래는 그대로 두고(지난달 기록 보존), CANCEL 행을 이번 달 음수 기여로 반영. 할부면 이번 달 이후 회차 voided, 음수 금액 = 원금 − 이미 지난 달에 반영된 회차 합 `[가정]`
4. **금액이 원거래보다 작음(부분 취소)**: 원거래 유지, 음수 CANCEL 행 반영
5. **못 찾음**: 음수 CANCEL 행 저장 + `CANCEL_UNMATCHED` needs_review(사용자가 원거래를 고르거나 그대로 둠)

**4.5 할부 일정**
- n개월 할부 금액 A → `q = floor(A / n / 100) × 100` (**100원 단위 내림**), 1회차 = `A − q×(n−1)`, 나머지 = q
  - 현대카드 명세서 7건으로 확인: 718,000/3 → 239,400·239,300·239,300 / 104,600/3 → 35,000·34,800·34,800 / 54,160/2 → 27,160·27,000 / 15,900/2 → 8,000·7,900
- 회차 k(1..n)의 month = 승인 월 + (k−1). 현대카드 명세서에서 이용월 명세서에 1회차가 청구되는 것을 확인함(6/07 할부 → 6월 이용분 명세서에 3/1)
- 롯데카드 할부 사례는 아직 없음 → 롯데 할부가 생기면 같은 규칙인지 확인 `[확인 필요]`

**4.6 내역 파일에 나오는 특수 행** (가져오기·알림 파서 모두 처리)
| 형태 | 예 | 처리 |
|---|---|---|
| 롯데 전액 취소 | 원거래 행에 `취소여부=Y`, `취소금액=−13,200` | 원거래 status=CANCELLED |
| 현대 부분 취소 | 같은 날 `티머니고속버스 13,200` + `−5,300` | 음수 행을 그대로 반영(4.4절 4번) |
| 롯데 해외 가승인 | 통화 비어 있음 + `매입여부=N` + 소액(1,526원) | 저장 안 함(롯데 월 합계에서도 빠짐) |
| 현대 연회비 | 가맹점 `연회비`, 수수료 칸 10,000 | 기타 카테고리 지출로 저장 |
| 현대 무이자 할부 | 배민 13,000원 2개월 등 소액 할부 | 일반 할부와 같음 |

- 조용한 시간에도 보내되 **소리·진동 없이** `[가정]`(사용자가 방금 결제한 직후라 맥락상 필요)
- 할부: 본문에 `· {n}개월 할부(이번 달 {회차금액}원)`, 해외: `· 해외`
- 같은 결제를 확인하면 알림을 지운다.

**확인 시트** (위→아래)
1. 결제 정보: 가맹점, 금액, 카드, 시각, (할부·해외 표시)
2. 카테고리 칩: 추천 칩이 선택된 상태. 가로 줄바꿈 칩
3. 특이 지출 토글: 기본 꺼짐. 보조 문구 "예산에는 포함되고, 평소 소비 통계에서는 빠져요"
4. 메모: 한 줄 입력, 최대 100자
5. [저장]

- needs_review 거래는 이유에 따라 시트 맨 위에 추가 입력을 띄운다(원화 금액, 카드 선택, 원거래 선택, 중복 여부).
- **학습**: 저장한 카테고리가 추천과 다르면 `merchant_rules[merchant_norm] = 새 카테고리`로 덮어쓴다.
- 미확인 거래도 S에 포함된다. 홈 화면에는 "확인 안 한 결제 {k}건"만 표시. 누르면 미확인 + 확인 필요 목록.

**기본 카테고리**: 식비 / 카페·간식 / 교통 / 게임 / 쇼핑 / 구독 / **API** / 통신 / 공과금 / 의료 / 교육 / **영화** / 경조사·선물 / **연회비** / 기타
- 굵게 표시한 3개는 실데이터 검수(10/13)에서 추가됨. API = 사용량 과금 AI·클라우드(OpenAI, Grok, Google Cloud 등), 구독 = 정액 멤버십

### F4. 예산 설정과 홈 화면 (P0)

**예산 설정** — 목표 방식을 고른다(10/13 결정)

| 방식 | 입력 | 월별 목표 |
|---|---|---|
| 고정 | 월 목표 금액 | 매월 같은 금액 |
| 단계적 | 시작 금액, 최종 목표, 기간(2~6개월) | 시작 → 최종 목표로 같은 폭씩 내림. 1만 원 단위 반올림. 마지막 달 이후는 최종 목표로 고정 |

- 단계적 예: 시작 80만, 최종 54만, 3개월 → 11월 80만 / 12월 67만 / 1월 54만
- 시작 금액 기본값: 최근 3개월 월평균(특이 지출 제외)을 1만 원 단위로 내림한 값. 실데이터로는 약 106만 원이며, 바로 고칠 수 있다
- 설정 화면에 각 달 목표를 미리 보여주고, 저장하면 `budgets`에 월별 행을 만든다(source=`STEP_PLAN`). 사용자가 특정 달 금액을 직접 고치면 그 달만 `MANUAL`로 바뀌고 나머지 계획은 유지
- 어떤 달에 목표를 넘겨도 다음 달 목표를 자동으로 바꾸지 않는다. 월말 회고(F8)에서 "다음 달 목표 그대로 갈까요?"만 묻는다 `[가정]`
- 바꾸면 이번 달부터 적용, 지난 달 값은 유지. 바꾼 날 base 재계산(3.6절)

**홈 화면** — 오늘 금액과 남은 예산을 **함께** 보여준다(10/13 결정, 전환 토글 없음)
```
┌─────────────────────────────┐
│ 오늘 쓸 수 있는 금액         │
│        8,500원              │  ← 가장 큰 숫자
│  (초과 시) 오늘 3,000원 초과 │
│ ─────────────────────────── │
│ 이번 달 남은 예산 216,000원  │  ← 보조 숫자(작게)
│ 남은 18일 · 정기 지출 115,000원 미리 뺌 │
│ (단계적 목표일 때) 11월 목표 80만 원 · 1/3단계 │
├─────────────────────────────┤
│ 확인 안 한 결제 2건      >   │
│ 다가오는 정기 지출           │
│  10/15 통신비 65,000원       │
│  10/25 가스비 약 50,000원    │
├─────────────────────────────┤
│ [💬 살까 말까 물어보기]      │
└─────────────────────────────┘
```
- **디자인**(10/16, `app/lib/ui/theme.dart`): 회색 바탕(#F2F3F5, 다크 #111316) 위 흰 카드(모서리 16), 강조색 파랑(#185FA5) 하나, 초과·많이 씀은 주황. 금액은 고정폭 숫자. 오늘 카드: 큰 숫자 아래 **예산 게이지** — 막대 = 이번 달 예산 중 쓴 비율(S ÷ B), 세로선 = 달이 지난 비율(오늘 ÷ 그 달 일수). 막대가 선보다 길면 날짜보다 빨리 쓰는 중이지만 색으로 판단하지 않고, 예산을 넘었을 때만 주황. 화면 순서: 오늘 → 달력 → 확인 안 한 결제 → 다가오는 지출 → 지출 분석. "살까 말까 물어보기"는 화면 아래 고정. 캡처: `docs/design/`
- **지출 달력**(10/16): 다가오는 정기 지출 아래에 월 달력. 칸마다 그날 쓴 금액(짧게: 8.5천, 1.2만, 12만), 칸 색은 그 달 가장 많이 쓴 날 대비 진하기만(초과·판단 색 없음). 이번 달 남은 날 중 정기·예정 지출이 있는 날은 점. 날짜를 누르면 그날 지출 목록 → 거래 수정 시트. 이전 달로 이동 가능. 할부 2회차부터는 그 달 1일에 잡힘(F8과 같음)
- 모든 스크롤 화면은 아래 여백에 시스템 내비게이션 바 높이를 더한다(Android 15 edge-to-edge, `app/lib/ui/insets.dart`)
- **초과하면 얼마나 넘었는지 금액으로 보여준다**(10/13 결정). 0원만 보여주고 끝내지 않는다
  | 상황 | 큰 숫자 자리 | 보조 문구 |
  |---|---|---|
  | 오늘만 초과 (`available < 0`, R ≥ 0) | 0원 | "오늘 {−available}원 넘었어요 · 내일부터 하루 {다음날 base 미리보기}원" |
  | 이번 달 초과 (R < 0) | 0원 | "이번 달 예산을 {−R}원 넘었어요" (남은 예산 줄에 표시) |
  | 정기 지출을 빼기 전엔 남지만 뺀 뒤 초과 (B − S ≥ 0, R < 0) | 0원 | 위 문구 + "예정된 정기 지출 {F}원을 반영한 금액이에요" |
  - 초과 금액은 보조 색(주황 계열)으로, 빨간색·느낌표는 쓰지 않는다(스트레스 최소화 원칙)
  - 다음날 base 미리보기 = 3.6절 공식에 내일 날짜를 넣어 계산(오늘 거래까지 S에 포함)
- **총 사용액(S)은 홈에 표시하지 않는다.** 상세(F8)에서만
- 데이터가 하나도 없으면(예산 미설정) 예산 설정 유도 카드만 보여줌

### F5. 정기 지출 (P0: 수동 등록 + 자동 탐지 제안)

**수동 등록 필드**: 이름, 금액, 추정 여부(체크 시 "약 X원" 표시), 결제일(1–31), 카드(선택), 가맹점 매칭 문구(기본값 = 이름)

**실제 결제와 매칭** (거래 저장 시)
- 조건: 활성 항목 중 `merchant_norm`이 match_pattern을 포함 AND 금액이 예정액 ±amount_tolerance_pct 이내 AND 승인일이 예정일 ±5일 이내 AND 이번 달 아직 PAID 아님
- **카드는 매칭 조건에 넣지 않는다.** 실데이터에서 8월에 Cursor·네이버플러스·카카오 구독이 현대 → 롯데로 옮겨갔는데, 카드를 조건에 넣으면 매칭이 끊긴다. card_id는 표시용
- **금액이 크게 변하는 항목**(전기 17,400~68,410원, 도시가스 1,370~9,780원)은 `is_estimate=true`, `amount_tolerance_pct=null`(금액 무시, 가맹점·날짜로만 매칭). 예정액은 최근 3개월 실제 금액의 중앙값 `[가정]`(P1 공과금 추정 전까지)
- 여러 개면 예정일이 가장 가까운 것 1개
- 매칭되면 `recurring_matches(PAID)` 생성 → F에서 빠지고 S로 들어감(차액 자동 반영). `decided_on`은 **결제일**로 둔다(오늘 결제면 오늘 → 3.6절 이중 차감 방지가 그대로 동작)
- **항목을 등록하면 지난 결제까지 거슬러 연결한다**(구현 10/13). 이번 달에 이미 낸 항목은 바로 F에서 빠지고, 지난 달 결제는 `recurring_item_id`가 붙어 평소 패턴 P에서 빠진다. 항목을 수정하면 자동 연결을 지우고 다시 만든다
- 확인 시트에서 [정기 지출로 연결] / [연결 해제] 수동 조정 가능

**월 예약형** (10/14 결정: 탈 때마다 알림이 없는 교통비)
- 정기 지출의 한 종류(`recurring_items.is_envelope`). 매달 예상액을 F로 미리 떼어 두고, 가맹점이 매칭 문구에 맞는 결제가 들어올 때마다 그만큼 줄어든다: **F 기여분 = max(0, 예상액 − 이번 달 연결된 실제 지출)**
- 매칭: 가맹점만 본다(금액·날짜 무관, 0원 환승 제외, 환불도 연결). 월별 처리 기록(recurring_matches)은 만들지 않는다
- 오늘 결제는 "오늘 0시 기준 남은 예약분" 안에서는 오늘 쓴 금액으로 치지 않는다(3.6절 이중 차감 방지와 같은 원리). 넘은 만큼만 오늘 지출
- 연결된 결제는 평소 패턴 P에서 빠진다
- 제안: 가맹점에 "후불"이 들어간 결제(토스 후불교통, 신한 모바일후불티머니)가 최근 30일에 5일 이상 있으면 "교통(후불)"로 제안. 예상액 = 결제한 날 하루 합계의 중앙값 × 이번 달 평일 수, 1,000원 단위 올림(실데이터: 3,100원 × 22일 → 69,000원)
- 실데이터 10/13: 10월 교통비 18,600원 사용 → 남은 예약 50,400원이 F에 들어감
- 실제 교통 결제는 월 1회 토스 후불교통 내역서를 가져오면 들어온다. 토스가 월 출금 알림을 보내면 F2 파서에서 함께 처리 `[확인 필요]`

**자동 탐지 제안** (`recurring_scan`, 하루 1회)
- 가장 최근 달부터 거꾸로, **한 달에 정확히 한 번씩 연속으로** 나온 구간을 본다(구현 10/13). 구간 안에서 결제일이 가장 최근 결제일과 3일 넘게 다르면 거기서 끊는다
- 조건: 그 구간이 연속 2개월 이상, 특이 지출·취소 아님, 마지막 결제가 이번 달이나 지난달(끊긴 구독 제외), 이미 등록된 항목·[아니요]한 가맹점 아님, 그리고
  - 금액 차이 ≤10% → 고정 금액 정기 지출(예정액 = 가장 최근 금액)
  - 금액 차이 >10% → 추정(공과금형, 예정액 = 최근 3개월 중앙값). **추정형은 연속 3개월 이상만** — 실데이터에서 편의점·고속버스가 2개월 우연히 겹쳐 잡히는 것을 거름
- 결제일 = 구간 결제일의 중앙값
- 같은 가맹점이 한 달에 여러 번 나오면 제외(배민·쿠팡처럼 자주 쓰는 곳이 정기 지출로 잡히지 않게)
- 실데이터 결과(테스트 R1, 10/13 기준 13개): Apple 3일, Cursor 6일, yesco 7일(추정), 교보문고 8일, 쿠팡 와우 10일, KT 인터넷 11일, KT 휴대폰 11일(추정), 피클플러스 17일, 카카오 23일, 네이버플러스 24일, 한국전력 26일(추정), 컬리 멤버스 27일, 배민클럽 28일. 모두 등록하면 10/13 기준 남은 F는 64,645원
- 나오면 안 되는 항목: 배달의민족, 쿠팡, 구글플레이, 교보문고(매달 8일쯤 3,500원이지만 금액이 가끔 달라 사용자 판단에 맡김 — 제안은 해도 됨)
- 제안은 앱 안 카드로만 표시("넷플릭스 13,500원이 매달 12일쯤 나가요. 정기 지출로 등록할까요?" [등록] [아니요]). [아니요]면 해당 가맹점은 다시 제안하지 않음
- 푸시 알림으로 보내지 않음(F7 하루 1회 예산을 쓰지 않기 위해) `[가정]`

### F6. 구매 상담 에이전트 (P0)

**채팅 화면**: 입력창 + 예시 칩("키보드 15만 원 살까?", "이번 주말에 5만 원 써도 돼?"). P0에서는 대화를 화면을 나가면 지움(로컬에도 저장 안 함). 상담 기록 저장은 P1(PRD F11)

**에이전트 루프** (서버는 상태 없음, 대화 기록은 앱이 보관)
1. 앱 → `POST /v1/agent` `{ items, round }` — `items`는 OpenAI Responses API 입력 항목(사용자 메시지, 모델 출력, `function_call_output`)
2. 서버 → 툴 정의·시스템 프롬프트를 붙여 `gpt-6.1-sol` 호출(`store=false`, 추론 항목은 암호화된 채로 돌려받아 앱이 다음 요청에 다시 보냄) → `{ status: "tool_calls", items, tool_calls }` 또는 `{ status: "final", text, items, verdict, verified, usage }`
3. tool_calls면 앱이 로컬에서 실행(`app/lib/core/agent_tools.dart`) → `function_call_output`을 붙여 다시 1번. **최대 5회 반복**, 넘으면 실패 처리
4. final은 서버가 숫자 검증(아래)까지 마친 답이다
- 툴 정의와 시스템 프롬프트는 **서버**에 둔다(`server/app/prompts.py`). 앱은 이름으로 실행만 한다
- 투자·대출·보험 등 범위 밖 질문은 서버가 키워드로 먼저 걸러 LLM을 부르지 않고 고정 문구로 거절한다
- 실측(10/14, 가짜 숫자 시나리오): 상담 1회 2~3 라운드, 약 4~11원

**툴 정의** (P0: `search_card_terms` 제외)
| 툴 | 입력 | 반환(JSON) |
|---|---|---|

**가맹점 조회**(10/21): 계산은 `app/lib/core/merchant_spending.dart`. 이름 맞추기는 부분 일치(띄어쓰기·(주)·기호 무시), 가맹점 정규화(배민 → 배달의민족 등)와 줄임말 몇 개(스벅·맥날 등), 두 글자 미만은 정확히 같을 때만. 특이 지출 포함, 할부는 그 달 회차, count는 결제 건수(할부 1건). usual_monthly = 최근 완료 3개월의 그 가맹점 월 합계 중앙값. 서버로 가는 것은 사용자가 말한 이름·찾은 가맹점 이름(최대 5개)·숫자뿐

**AI 소비 분석**(10/20): `get_spending_insights`(입력 없음) — 계산은 `app/lib/core/insights.dart`.
- 평소 한 달 = 최근 완료 3개월 지출(특이 지출 제외)의 중앙값. 앞쪽 달 지출이 나머지 중앙값의 1/3 미만이면 기록이 덜 들어온 달로 뺀다. 추세 = 최근 3개월 평균 − 그 전 2~3개월 평균
- 아낄 곳 후보(월 절약액, 100원 내림, 큰 순 최대 4개): ① 카테고리: 평소 − (최근 완료 달 중 **실제로 쓴 달**의 최저), 평소의 절반 상한, 5천 원 이상, 줄이기 어려운 카테고리(통신·공과금·구독·연회비·교통·의료·교육) 제외 ② 소액 결제(1만 원 미만, 위 카테고리·①에 잡힌 카테고리 제외) 합의 절반 ③ 구독 2개 이상이면 평균 한 개 금액
- 심야 비율은 시각을 아는 결제 10건 이상일 때만(내역 파일에 시각이 없는 카드가 있음)
- 가맹점(10/20): 카테고리별 상위 3곳(최근 3개월 월평균), 지난달 구독 목록(이름·금액), 소액 결제가 잦은 곳 상위 3(월평균 건수). 이름은 `maskIdentifiers`를 거쳐 보낸다. 날짜별 거래 원본은 보내지 않는다
- 응답 형식: [특징] 2~3 · [아낄 수 있는 곳] 후보 순서대로 · [앞으로] 1~2. 지출 분석 화면 "아낄 수 있는 곳" 카드가 같은 결과를 바로 보여주고 [AI에게 분석·상담 받기]로 이어진다

**일상 대화형 상담**(10/16): 구매 질문이 아닌 "예산 넘었는데 어캄", "어디서 많이 썼어?", 잡담에도 답한다.
- `plan_recovery` 계산: `over = S + F + P − B`(평소대로 쓰면 월말 초과), `target = P − over`(남은 기간 변동 지출 한도).
  `over ≤ 0` → on_track. `target ≥ 0` → recoverable: `daily_cut_needed = ceil(over ÷ N)`(100원 단위 올림), `daily_spend_target = floor(target ÷ N)`(100원 단위 내림).
  `target < 0` → not_recoverable: 하루 감축액은 **주지 않는다**(평소 하루 소비보다 커서 실현 불가, 평가 v4) → `over_even_if_zero_spend = −target`
- 줄일 곳 후보: 지난 완료 달(최대 3개)의 같은 남은 기간 카테고리별 소비 중앙값 상위 3개. 통신·공과금·구독·연회비·교통·의료·교육은 뺀다. `half_saves` = 그 절반(100원 내림)
- `compare_spending`: 이번 달 1일~오늘 vs 지난 달들 같은 기간(카테고리별 중앙값), 지난달 전체 vs 그 전 3개월. 특이 지출 제외
- 집계만 서버로 간다. 가맹점 단위 조회는 하지 않는다(가맹점 이름을 LLM에 보내야 하므로 별도 결정 필요, PRD 12장)
- 잡담·감정에는 툴 없이 1~2문장, 금액 없이

- 툴 결과의 금액은 정수로 보내고, 표시용 문자열(`"150,000원"`)도 함께 넣어 LLM이 그대로 인용하게 한다.

**응답 형식** (시스템 프롬프트로 강제, 구매 질문. 상황 상담은 `[지금]`·`[이렇게 하면]` 2~3줄)
```
[판단] 괜찮아요 | 조건부 | 미루는 걸 추천
[근거] 남은 예산, 남은 일수, 예정 고정비, 평소 남은 기간 소비 — 툴 숫자만
[대안] 1~2개 (예: "다음 달 1일 이후", "이번 주 외식 2번 줄이면 가능")
```
- 판단 문구는 `simulate_purchase.verdict`와 1:1 대응. 다르면 검증 실패로 본다.
- 말투: 비난 없음, "앞으로"에 초점, 총액 강조 금지.

**숫자 검증**
1. 최종 텍스트에서 **금액**만 추출(`216,000원`, `15만 원`, `21만 6천 원`, `5천 원` → 정수). 횟수·날짜·퍼센트("2번", "12일", "10%")는 대안 제시에 자연스럽게 나오므로 검증하지 않는다(구현 10/14)
2. 각 금액이 툴 결과 또는 사용자 메시지에 나온 금액(표시용 100원·1천 원·1만 원 단위 내림과 부호 뺀 값 포함)인지 확인. 판단 문구가 `simulate_purchase.verdict`와 다르면 실패
3. 실패 → 실패 내용을 붙여 1회 재생성 → 또 실패 → "계산을 확인하지 못했어요. 홈 화면의 숫자를 확인해 주세요." (숫자 없이)

### F8. 카테고리·기간 보기 (P0) — 화면 이름 "지출 분석"(10/16)

- **이번 달 흐름**(10/16, 기간이 이번 달이고 예산이 있을 때): 1일~오늘 누적 지출(실선), 오늘 → 말일 "평소대로 쓰면"(점선, 끝값 = 지금까지 + 남은 정기·예정 지출 F + 평소 남은 기간 소비 P = 3.8절의 E), 지난 완료 달(최대 3개) 같은 날까지 누적의 중앙값(회색), 예산(가로 점선). 위에 "평소대로 쓰면 월말 약 X원 · 예산보다 Y원 많아요/여유" 한 줄. 계산 `core/analysis.dart monthPace`
- **평소와 비교**(10/16, 이번 달·지난달): 카테고리별 (이번 기간 − 평소)를 가운데 0 기준 좌우 막대로. 평소 = 지난 완료 달(최대 3개) 같은 기간의 카테고리별 중앙값, 특이 지출 제외. 차이 큰 6개만. 많이 쓴 쪽은 주황(빨강 안 씀). 상담 툴 `compare_spending`과 같은 함수(`compareCategories`)

- 기간: 이번 달 / 지난달 / 최근 3개월 / 직접 지정(시작~끝 날짜)
- 합계 기준: **월 기여액 기준**(3.2절). 일시불은 승인일, 할부 1회차는 승인일, 2회차부터는 해당 월 1일에 있는 것으로 본다(구현 10/14). 달 단위로 보면 S와 정확히 같다(실데이터 5~10월 테스트)
- 상단: 기간 총액(여기서만 총액 노출) + 특이 지출 포함/제외 토글(기본 포함)
- 목록: 카테고리별 합계, 비율(%), 막대. 미분류(category_id=null)는 "미확인"으로 묶음
- 카테고리 탭 → 거래 목록(날짜, 가맹점, 금액, 할부 회차, 메모, 특이 지출 표시 ★, 카드). 거래 탭 → 확인 시트(F3와 같은 시트: 카테고리 칩, 특이 지출, 메모)
- **최근 6개월 추이**(구현 10/14): 월별 누적 막대. 상위 5개 카테고리는 고정 순서 색, 나머지는 회색 "그 외". 막대를 길게 누르면 카테고리별 금액
- 확인 시트에서 카테고리를 바꾸면 MerchantRule을 학습하되, 결제대행형 가맹점(네이버페이, 카카오페이, 토스페이, 페이코, 구글플레이, 구글클라우드코리아)은 학습하지 않는다
- 거래 직접 추가(MANUAL): 현금 결제 등. 금액, 날짜, 가맹점, 카테고리, 특이 지출, 메모 — **미구현**
